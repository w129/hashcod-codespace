# Platform access period

The Beautiful UI card below Files offers 10 days by default, with 20, 30 and 60 days as alternatives. Before any platform use, a non-dismissible Beautiful UI dialog requires selecting and confirming 10, 20, 30 or 60 days. Choosing alone does not grant access. The workspace stays inert during verification, on save failure and until confirmation succeeds. The card below Files shows the confirmed period; its alternatives can be inspected but cannot change an active period. Each day is 86,400 seconds. An active period cannot be extended by accepting again. The selection concerns access, not automatic deletion or expiry of uploaded files.

`/api/platform-period` forwards the signed, HttpOnly cookie identity to the existing shared-cloud Edge Function. A private Postgres ledger supplies the deadline and the Edge Function uses database time. The PHP cookie is signed and host-bound; browser-provided tokens and dates are ignored. Reloading restores the selected days and deadline from the server. The live timer uses server time and a monotonic clock, including when a previously accepted desktop session temporarily loses its connection.

At expiry the application becomes inert and shows a Beautiful UI renewal dialog. Workspace/file APIs and `/api/` routes deny missing, unconfirmed, malformed and expired periods. Direct controller aliases use the same guard. Only the period endpoint, entrance proof endpoints and runtime security configuration/status needed to bootstrap entry remain reachable before confirmation; they do not grant workspace access. The user enters the renewal key and chooses a new period. Renewal attempts are rate limited and only a SHA-256 verifier of the long random key exists in the private configuration table. Neither the key nor the identity token appears in public HTML, JavaScript or responses. Existing entrance and per-file access-code checks remain in force.

The platform currently has an anonymous shared workspace, so the access identity belongs to the browser and host. Clearing its cookies or using another browser/device creates a new anonymous identity and requires mandatory confirmation again. This cannot skip selection, but it can reset an anonymous deadline; account-wide identification would require authenticated accounts. This feature is not an account-wide subscription or a paid entitlement. Enforcing a duration across all devices and resisting identity resets requires authenticated accounts; uploaded files continue to share across devices as before.

Apply `20261007011139_platform_access_period.sql` and deploy all sources in `supabase/functions/hashcod-shared-cloud`. Provision the SHA-256 verifier privately in `hashcod_shared.access_period_config`, singleton row `id=1`; never add credentials to migrations. The existing Edge deployment uses custom HMAC authentication and retains its existing JWT setting. No hosting-provider environment change is needed. Both hosted PHP and the Windows package use the canonical sources and the same cloud ledger. Choosing or renewing a period requires a connection.

Verification: `tests/security/test-platform-period.php`, `tests/e2e/test_platform_period.js`, and Chromium `tests/e2e/test_platform_period_browser.js` cover missing/choose default denial, direct-controller bypass attempts, mandatory initial selection, Escape, failure to confirm, signed deadlines, reload, failure to save, expiry, wrong-key rejection, renewal, focus and phone sizing. The shared-files regression also checks all four choices and preservation during file synchronization.
