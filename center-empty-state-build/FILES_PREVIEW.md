# Protected Files explorer

The Files explorer appears directly below the Open Hatch action row. The same File Vault state feeds the explorer and upload window. Metadata loads on mount and refreshes on upload, focus and restored cloud state; local metadata is available while the bounded cloud request is pending. IDs, not filenames, identify selected files.

Opening a file invokes `HashcodFileVaultTotp.preview(file)`. The existing chosen-code / legacy TOTP dialog is required on every opening. Device bytes are decrypted only after the exact code is verified; cloud previews reuse the server-authorized download POST. Cancellation, invalid codes and server errors never open a viewer or create a content URL. No authorization code, token or decrypted copy is persisted. Download and deletion from the preview request the code again.

PDFs render as canvas with pinned PDF.js 6.4.299, one page at a time, using a local worker, fonts and decoders generated by the build. PDF eval and XFA are disabled. No iframe or relaxed CSP is needed. Images, browser-supported audio and video use temporary Blob URLs revoked when the preview closes. Text/code/HTML/SVG are escaped React text, limited to the first 2 MB. Other formats show file details and a protected download; no scripts, archives or executable attachments are executed.

Both the Docker build and Windows build compile the same explorer and PDF assets. Device-only files remain scoped to that browser profile; cloud files use the existing authorized global file index. This change does not configure cloud storage or migrate unprotected legacy device files.

Checks: real built bundles in JSDOM on hosted/loopback origins, existing upload/download/delete regression tests, and Chromium with actual encryption, PDF worker/canvas rendering, reload, code retries, deletion, inert HTML and frame geometry at desktop/mobile/short viewport sizes. Chromium visual evidence is attached to the universal workflow.
