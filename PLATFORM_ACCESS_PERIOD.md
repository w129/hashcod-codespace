# Checkout, free session and Hashcod Pro

The checkout follows `Checkout-html (1).zip`. Prices are US$2,000 monthly / US$19,200 yearly (20% annual discount); they live in `PLAN_PRICES` in `center-empty-state-build/checkout-data.js`. Benefits: Toolbook, AI permission/certification, tools and +20 requests/month, implemented as **25 requests per UTC calendar month**. Existing BYOK requirements, consent, model budgets, signatures, file access codes and isolation still apply. The free tier exposes presentation, FAQ, plans and administrative sign-in; it grants **zero** Pro requests or tool/cloud/certification permissions.

## Activation and advisor workflow

1. The checkout loads a host-bound, HttpOnly signed session identity. Only its public UUID reference reaches the UI; no session MAC/token is disclosed. WhatsApp opens a draft to `+1 829 472 1257` with chosen plan/period/total, country, fiscal preference and activation reference. RD requires 11 cédula digits as a format check only. Other-country drafts exclude it.
2. The advisor independently confirms actual receipt of payment; no WhatsApp click, amount, client flag, technical session or legacy renewal key proves payment.
3. In **Administrar pagos**, sign in using the existing private-requests admin key. Enter the reference from the customer's WhatsApp draft, select the actually paid plan and confirm receipt. The signed admin ticket, revision, session binding, expiry and rate limits are verified by the Edge Function. No new admin secret or bypass is introduced.
4. **Emitir código de activación** shows a cryptographically random six-digit code once, for manual delivery over WhatsApp. It is bound to that reference, expires in 15 minutes, and replaces any prior unused code. Owner-bound HMACs, never plaintext codes, are stored. Prior codes are never reused for that owner.
5. The customer enters it in the same browser/application session. Redemption is atomic and one-use, with six attempts per identity and 300 per IP per 15 minutes (a shared proxy may aggregate several customers). Database time and the advisor's stored plan set one calendar month / 12 months; unused paid time is retained on renewal. No payment gateway is connected: the advisor's receipt confirmation is the payment authorization.

The cédula stays in mounted React state and the WhatsApp draft, never platform storage or API calls. The code stays in React state until it is submitted to the same-origin redemption API; it is neither persisted client-side nor logged. Closing checkout clears personal inputs. Admin issuance responses are no-store. The plaintext code is not stored in the database. Losing/clearing the signed browser session means its reference changes; the advisor must issue for the correct reference.

## Enforcement and persistence

`POST /api/platform-period {entry:"free"}` creates/restores the same renewable 10-day technical session. This duration has no relationship to paid entitlement. `GET` reports `subscription` and reference. `{entry:"pro",code:"......"}` forwards only the cookie token and six-digit code to `subscription.redeem`, then re-fetches status and seals the server-confirmed Pro deadline in the host-bound HttpOnly cookie. Body tokens, prices, plan, dates, durations and paid flags cannot upgrade access. Existing sessions start free; legacy `period.accept` only affects technical sessions.

PHP runtime routes and direct controllers deny missing/forged/expired periods and deny Pro functions without a valid signed Pro deadline. Cloud operations independently check the private subscription ledger: files' content/uploads/deletions, shared state, editor identity, tokenization submission, AI review and certificates. Public certificate verification/revocation listings and public shared-file metadata remain readable. Admin requests management remains protected by its own admin key and is available without a paid subscription; the administrative payment endpoint does not need Pro. The separate private-requests button opens only the admin-key form. Admin certificate revocation requires its existing signed admin ticket and CSRF proof, rather than a personal subscription. UI state, datasets, local storage or manually firing a browser event cannot authorize backend operations.

The editor identity deadline is capped to the paid deadline so its existing JWT/Redis expiration and periodic verification respect Pro expiry. Review bridge checks Pro on each non-admin operation. Technical-session refresh retains request/project ownership and does not extend Pro. Paid expiry hides/closes tools when status refreshes; server denial takes effect immediately by its own clock. Offline free use cannot unlock paid tools.

The 25/month request quota locks the subscriber row and checks UTC month counts inside the same transaction as canonical request insertion. Concurrent tabs cannot overrun it; a retry of an already-submitted file does not consume another request. Validation failures do not consume quota. No files, certificates or projects are deleted on expiry.
